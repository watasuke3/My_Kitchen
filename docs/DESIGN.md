## 1. アーキテクチャ概要

```
┌────────────────────┐         ┌──────────────────────┐         ┌──────────────┐
│  ブラウザ           │  HTTPS  │  バックエンド          │  JDBC   │  PostgreSQL   │
│  React SPA         │ ──────▶ │  Scala / Play         │ ──────▶ │              │
│  (Vite ビルド)      │  REST   │  Framework            │         │              │
└────────────────────┘         └──────────────────────┘         └──────────────┘
```

- **構成**: SPA + REST API の典型構成。フロントとバックは別プロセス・別ビルド。
- **データ集約**: ユーザーデータは PostgreSQL に集約。フロントには永続データを持たない（ログイン情報のセッショントークンのみ保持）。
- **マルチデバイス**: サーバー集約型のため、別端末からのアクセスでも常に最新データが見える。

## 2. 技術スタックと選定理由

| レイヤ | 採用 | 主な選定理由 |
|---|---|---|
| バックエンド言語 | **Scala 2.13** | 学習目的が主軸だが、Play 公式テンプレートが 2.13 デフォルトで情報量・サンプル量が圧倒的に多い。Scala 3 とは文法寄りの差で本質学習への影響は小。Phase 1 でこの判断に切り替え（DESIGN.md 当初は Scala 3 を予定していた）。 |
| Web フレームワーク | **Play Framework** | 学習者向けのドキュメントが厚く、Future ベースで http4s/ZIO より理解しやすい。 |
| ORM / DB アクセス | **Slick** | Play との組み合わせが定型化。詰まりにくい。 |
| マイグレーション | **Flyway** | スキーマ管理の業界標準。 |
| ビルドツール | **sbt** | Scala の標準。学習対象として適切。 |
| DB | **PostgreSQL** | 採用確定。 |
| フロント言語 | **TypeScript** | 型安全。フロント / バック双方で型を意識する経験が積める。 |
| フロント FW | **Vite + React** | 認証必須のアプリには SSR 不要。SPA 構成が学習者にとって役割分離が明快。 |

### 採用しなかった候補とその理由

- **http4s / ZIO HTTP**: 関数型・エフェクトシステムの学習負荷が高く、Scala 文法習得と並行は厳しい。Play 習熟後の選択肢として保留。
- **Next.js**: SSR / App Router の学習コストに対し、認証必須のこのアプリでは恩恵が薄い。
- **Scala.js + Laminar**: フロントまで Scala 統一は魅力だが、エコシステム・情報量が React に大きく劣る。

## 4. 型共有戦略（フロント / バック間）

スキーマや API レスポンスの型を Scala と TypeScript で重複定義する問題への対応方針。

### 段階的アプローチ
1. **初期（Phase 3〜5 前後）**: 手書きで TS 側に型を定義。規模が小さいうちは現実解。
2. **中期（Phase 6 以降）**: **Tapir** を導入し、Scala 側で API を型として記述 → OpenAPI 仕様書を自動生成 → TS クライアントを `openapi-typescript` 等で自動生成。

**理由**: いきなり Tapir を導入すると Play の標準的な書き方とは離れてしまい、学習目的を阻害する。基本に慣れてから乗せる。

## 5. 栄養計算の仕様

### 基礎代謝量（BMR）
- **採用式**: 国立健康・栄養研究所の式（Ganpule の式）
- **計算式**:
  ```
  BMR (kcal/日) = ((0.0481 × W + 0.0234 × H − 0.0138 × A − 性別係数) × 1000) ÷ 4.186
  ```
  - `W`: 体重 (kg)
  - `H`: 身長 (cm)
  - `A`: 年齢
  - **性別係数**: 男性 `0.4235`、女性 `0.9708`

### 1日あたりの必要カロリー
- **計算式**: `必要カロリー = BMR × 活動レベル係数（PAL）`
- **活動レベル係数**（日本人の食事摂取基準2020 に準拠）:
  - 低い (I): **1.50**
  - ふつう (II): **1.75**
  - 高い (III): **2.00**

### PFC バランス
- 目標設定（ダイエット / 維持 / 筋力アップ等）に応じて P / F / C 比率を変える。
- **具体的な比率は Phase 5〜6 で確定**（栄養学的根拠の調査が必要）。

## 6. データ同期方針

- **真実の場所（Source of Truth）**: サーバー側 PostgreSQL。
- **クライアント側**: TanStack Query のキャッシュのみ。永続化はしない（IndexedDB 等は使わない）。
- **マルチデバイス**: サーバーから毎回取得するため自然と複数端末で整合性が取れる。
- **将来拡張**: WebSocket / SSE によるリアルタイムプッシュ、楽観的更新の高度化、競合解決はロードマップ送り。

## 8. 段階的実装計画

学習目的を踏まえ、機能を一気に作らず段階的に積み上げる。

| Phase | ゴール | 主な学習要素 |
|---|---|---|
| **0** | 環境構築 | Scala / Node / PostgreSQL のセットアップ |
| **1** | バックエンド Hello World | Play のディレクトリ構造、ルーティング、コントローラー |
| **2** | フロントエンド Hello World | Vite, React, JSX, TS の基本 |
| **3** | フロントとバックを HTTP で繋ぐ | CORS、`fetch`、API レスポンスの型付け |
| **4** | ユーザー登録・ログイン | 認証、パスワードハッシュ、セッション or JWT |
| **5** | レシピの CRUD | DB スキーマ、Slick、フォーム、バリデーション |
| **6** | 献立カレンダー / 買い物リスト | 関連テーブル、集計、UI 状態管理 |
| **7** | 栄養計算・フィードバック | 計算ロジック、リアルタイム集計 |
| **8** | アレルギー除外、人数スケーリング、重複回避 | アルゴリズム的要素 |

各 Phase 完了時に動くものができていることを優先（半端な機能で次に進まない）。

## 11. 会話の経緯メモ（決定の背景）

設計判断の **「なぜそうなったか」** を後から辿れるように。

- **2026-04-27**: 要件レビューを実施し、年齢・活動レベルの追加、セキュリティ要件の明文化、調味料の数値化方針、買い物リストの合算と同期、Derived レシピの本人限定可視性、調理手順の追加、人数スケーリング、献立の重複回避（直近1〜2週）、食事実績の手動記録（食べた / 食べなかった）、目標設定をプロファイルへ統合、を決定。
- **2026-04-27**: バックエンドを Scala に確定。理由は学習目的。フロントエンドも切り替え可と提示があったが、TypeScript を維持する方針で合意。
- **2026-04-27**: フロントエンドを **Vite + React + TypeScript** に確定。Next.js は SSR が活きないため不採用。
- **2026-04-27**: バックエンド Web フレームワークは **Play Framework** を第一候補に確定。http4s / ZIO HTTP は学習負荷から後回し。
- **2026-04-28**: Phase 1 で `sbt new playframework/play-scala-seed.g8` を実行した結果、テンプレートが Scala 2.13 デフォルト。当初の Scala 3 方針を **Scala 2.13 に変更**。理由は (1) 公式テンプレートの組み合わせが安定、(2) ネット情報・チュートリアルが 2.13 圧倒的多数、(3) 2.13 と 3 の差は文法寄りで本質学習への影響が小さい、ため。Play 3.0.10 + Java 21 + Scala 2.13.18 構成で `http://localhost:9000` の Hello World 動作確認済み。
- **2026-05-18**: レシピ管理の要件を変更。「ユーザーが食材・手順を自前入力するモデル」から「クックパッド等の外部サイト URL を貼り付けて登録するモデル」へ転換。これにより Ingredients テーブルは廃止、Recipes テーブルに `source_url` / `category` / `servings` / `memo` を持つシンプルな構造に変更。栄養計算（Phase 7）は食材データが存在しないため、手動入力 or スクレイピングで対応するか Phase 後送りで検討。
