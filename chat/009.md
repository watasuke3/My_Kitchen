# assistant
**IPアドレス単位を推奨する理由**

- CLAUDE.mdのセキュリティ要件は「ログインAPIへのレート制限（ブルートフォース対策）」であり、これは「同一送信元からの大量試行を止める」という意味が主目的です。IP単位はまさにこれに直接効きます。
- メールアドレス単位だと、攻撃者が特定の1アカウントに絞ってパスワードを大量試行するケース（クレデンシャルスタッフィングの標的型）は防げますが、逆に「他人のメールアドレスを使って大量にログイン試行し、正規ユーザーを締め出す」DoS的な悪用が可能になります（メールさえ知っていればロックできてしまう）。IP単位ならこの弱点がありません。
- 実装コストが低い。play-guardのIPフィルタ機能はAction合成だけで完結し、AuthServiceやDBに手を入れる必要がありません。今のAuthServiceは`Either`ベースの薄いロジックで綺麗なので、これを崩したくない。
- 個人開発・学習目的の現段階では、まずIP単位で「何も対策がない」状態を解消するのが費用対効果が良く、必要になればメール単位を後日追加できます（今回は拡張の余地を潰しません）。

**AccountLocked / MaxFailedAttemptsを削除してplay-guardに一本化する理由**

- 今の`AccountLocked`は「呼ばれることのない到達不能コード」です。CLAUDE.mdの方針「未使用のimport・変数は残さない」に反しています。
- 制限ロジックをAuthController側のAction合成（play-guardのフィルタ）に持たせる設計にすると、認証ドメインロジック（AuthService）とインフラ的関心事（レート制限）が分離され、責務が明確になります。
- 中途半端に両方残すと、「AuthServiceのMaxFailedAttemptsは何に効いているのか」を将来読んだときに誤解を招きます（実際には何もしていないため）。

この理由を踏まえて、決定をお願いします。
